# Jula Governor Workspace Spec

This repository houses the configuration components, data adapters, and executable rule criteria for the Jula Continuous Assurance Platform. It isolates high-level compliance checklists from raw execution code, delivering an automated, auditable security posture.

---

## 🛠️ Repository Architecture Blueprint

```text
jula-governor/
├── workspace.yaml           # Active provider scopes and targets
├── catalog.csv              # Raw multi-framework corporate controls list
├── requirements.csv         # Intermediate engineering threshold triage sheet
│
├── engine/                  # Flat Engine Directory (Unopinionated Runtime)
│   ├── integrations/        # YAML data collectors (gcp.yaml, aws.yaml, etc.)
│   ├── translators/         # Rego payload adapters (gcp_storage.rego, gcp_database.rego, etc.)
│   ├── schemas/             # Optional custom/proprietary JSON schemas (empty by default)
│   └── prompts/             # Centralized AI prompt text templates
│       ├── 01_build_integration.md
│       ├── 02_build_translator.md
│       ├── 02_heal_translator.md
│       ├── 04_extract_requirements.md
│       └── 06_generate_policy.md
│
└── policies/                # Executable Policy Code Tier
    ├── scoping/             # Environment filters and global waivers
    └── rules/               # Flat, compiled Rego policies
```

### 1. `workspace.yaml` (Root Directory)
The master orchestration configuration file acting as the platform's system boundary toggle switch. It explicitly declares which providers and SaaS integrations are active within this workspace.

### 2. `catalog.csv` (Root Directory)
The active business compliance checklist framework provided by the risk team. It is a strictly pruned, 3-column spreadsheet (`Control_ID`, `Control_Statement`, `Control_Description`) exported from corporate GRC utilities. It is overwritten directly whenever master compliance frameworks are updated.

### 3. `requirements.csv` (Root Directory)
The intermediate engineering triage workspace generated by the AI. It structures unstructured prose from the catalog into clear technical parameters (such as expected values and operators) with a `PENDING` status column, allowing human operators to explicitly review, approve, or skip targets before they are compiled into code.

### 4. `engine/` (Flat Engine Directory)
Houses the foundational engineering properties defining how Jula interfaces with infrastructure systems. All files live directly in their respective root directories with no nested subdirectories.

- `engine/integrations/`: Dictates the connection parameters and credential scopes specifying exactly where and how collectors harvest infrastructure configurations. Each provider gets a single YAML file (e.g., `gcp.yaml`, `aws.yaml`, `github.yaml`).
- `engine/translators/`: Houses the OPA Rego scripts responsible for flattening complex native provider payloads into uniform, predictable key-value fields. Files follow the `{{PROVIDER}}_{{SERVICE}}.rego` naming convention (e.g., `gcp_storage.rego`, `gcp_database.rego`). Package declarations use the flat namespace `package translators.{{PROVIDER}}_{{SERVICE}}`.
- `engine/schemas/`: An optional, client-managed registry housing flat structural definitions (`{{PROVIDER}}_{{SERVICE}}.json` or `{{TOOL}}.json`) for custom, private, or proprietary APIs. Because Jula leverages the pre-trained weights and public open-standard knowledge of advanced AI models for primary cloud hyperscalers (AWS, Azure, GCP), this directory remains completely empty by default in core operations. It serves as an on-demand dictionary to feed custom structural fields into the prompt engineering tier if a client decides to onboard a non-public, custom internal service.
- `engine/prompts/`: A centralized vault for text-based system prompts utilized by AI agents. Houses strictly templated constraints mapping the translation flow from business prose through policy compilation and autonomous self-healing of translator drift.

### 5. `policies/` (Executable Evaluation Directory)
The active, machine-readable gating tier evaluated by the Jula runtime engine.

- `policies/scoping/`: Global interceptor logic managing environmental exclusions, asset tagging context, and active corporate waivers.
- `policies/rules/`: The output landing zone for automated policy generation. All active evaluation rules live flat inside this folder alongside a single `manifest.json` file tracking rule updates. Historical points-in-time are audited directly via Git version control tracking.

## 🔄 The 7-Step Operational Lifecycle

[1. Integrations] ──► [2. Translators] ──► [3. Import Catalog] ──► [4. Extract Requirements]
│
[7. Run Evaluation] ◄── [6. Generate Policies] ◄── [5. Review Requirements] ◄───┘

1. **Integrations:** Collectors utilize the credential parameters and endpoint mappings configured inside `engine/integrations/` to pull raw infrastructure metadata payloads based on the active providers turned on in `workspace.yaml`.
2. **Translators:** Automated Rego data adapters process raw responses from providers, flattening complex structures into predictable key-value properties.
3. **Import Catalog:** The risk team seeds the compliance workspace by dropping their master, multi-framework corporate control checklist directly into `catalog.csv`.
4. **Extract Requirements:** Leveraging centralized prompt contexts (`engine/prompts/04_extract_requirements.md`), Jula's AI reads the unstructured prose controls and extracts explicit, measurable technical constraints into `requirements.csv`.
5. **Review Requirements:** An intermediate spreadsheet workspace (`requirements.csv`) displays the AI's extracted parameters, allowing human operators to confirm, adjust, or skip constraints via the status column.
6. **Generate Policies:** Leveraging centralized prompt contexts (`engine/prompts/06_generate_policy.md`), an automated generation script reads approved rows from the spreadsheet and writes immutable, standalone `.rego` rule blocks directly into the flat `policies/rules/` directory.
7. **Run Evaluation:** The single centralized Jula Evaluator Engine ingests the rules directory, executes the policies against live infrastructure payloads, filters outputs based on global `policies/scoping/` criteria, and logs the continuous audit trail straight to the Standardized Findings Ledger.

## 🤖 The GitOps Self-Healing Loop

The Governor repository acts as the central hub for the Jula automated self-healing loop. 

If the downstream `jula-evaluator` daemon detects a native API schema drift during runtime, it dispatches a webhook directly to `.github/workflows/self_heal.yml`. This pipeline extracts the breaking payload, executes `cmd/translate` to dynamically re-map the Rego translator logic, and generates a Pull Request with the fix.
