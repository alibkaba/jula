# Jula Compliance-as-Code Workspace Spec

This repository houses the configuration components, data adapters, and executable rule criteria for the Jula Continuous Assurance Platform. It isolates high-level compliance checklists from raw execution code, delivering an automated, auditable security posture.

---

## 🛠️ Repository Architecture Blueprint

### 1. `workspace.yaml` (Root Directory)
The master orchestration configuration file acting as the platform's system boundary toggle switch. It explicitly declares which out-of-the-box cloud providers and custom application extensions are active within this workspace. If a tool is omitted here, the execution engine completely ignores its corresponding subdirectories.

### 2. `catalog.csv` (Root Directory)
The active business compliance checklist framework provided by the risk team. It is a strictly pruned, 3-column spreadsheet (`Control_ID`, `Control_Statement`, `Control_Description`) exported from corporate GRC utilities. It is overwritten directly whenever master compliance frameworks are updated.

### 3. `requirements.csv` (Root Directory)
The intermediate engineering triage workspace generated by the AI. It structures unstructured prose from the catalog into clear technical parameters (such as expected values and operators) with a `PENDING` status column, allowing human operators to explicitly review, approve, or skip targets before they are compiled into code.

### 4. `engine/` (Central Platform Directory)
Houses the foundational, hands-off engineering properties defining how Jula interfaces with infrastructure systems.
- `engine/integrations/`: Dictates the connection parameters and credential scopes specifying exactly where and how collectors harvest infrastructure logs (divided into `core/` for built-in clouds and `extensions/` for custom SaaS tools).
- `engine/schemas/`: Holds the structural JSON/OpenAPI signatures detailing the fields an app exposes. It consists entirely of the `extensions/` sub-directory where user-onboarded custom application specifications are maintained (e.g., `extensions/github.json`) to drive the AI extraction engine without local third-party validation boilerplate.
- `engine/normalizers/`: Houses the OPA Rego scripts responsible for data flattening. They catch complex vendor payloads and normalize them into uniform, clean fields (e.g., `require_tls`).

### 5. `policies/` (Executable Evaluation Directory)
The active, machine-readable gating tier evaluated by the Jula runtime engine.
- `policies/scoping/`: Global interceptor logic managing environmental exclusions, asset tagging context, and active corporate waivers (e.g., ignoring development sandboxes across both cloud resources and SaaS connections).
- `policies/rules/`: The output landing zone for automated policy generation. It avoids complex folder hierarchies and physical date subdirectories. All active evaluation rules live flat inside this folder (prefixed as `core_*` or `ext_*`) alongside a single `manifest.json` file tracking rule updates. Historical points-in-time are audited directly via Git version control tracking.

## 🔄 The 7-Step Operational Lifecycle

[1. Integrations] ──► [2. Normalizers] ──► [3. Import Catalog] ──► [4. Extract Requirements]
│
[7. Run Evaluation] ◄── [6. Generate Policies] ◄── [5. Review Requirements] ◄───┘

1. **Integrations:** Collectors utilize the credential parameters and endpoint mappings configured inside `engine/integrations/` to pull raw infrastructure metadata payloads based on the active tools turned on in `workspace.yaml`.
2. **Normalizers:** Automated Rego data adapters process raw JSON responses, flattening complex, deeply nested vendor structures into predictable key-value properties.
3. **Import Catalog:** The risk team seeds the compliance workspace by dropping their master, multi-framework corporate control checklist directly into `catalog.csv`.
4. **Extract Requirements:** Jula's AI reads the unstructured prose controls and references active tool definitions inside `engine/schemas/` to extract explicit, measurable technical constraints into `requirements.csv`.
5. **Review Requirements:** An intermediate spreadsheet workspace (`requirements.csv`) displays the AI's extracted parameters and matching confidence scores, allowing human operators to confirm, adjust, or skip constraints via the status column.
6. **Generate Policies:** Once approved, a deterministic code generation script reads the rows, invalidates the temporary staging entries, and writes immutable, standalone `.rego` rule blocks directly into the flat `policies/rules/` directory while recording metadata updates in the root manifest ledger.
7. **Run Evaluation:** The single centralized Jula evaluator engine ingests the rules directory, executes the policies against live infrastructure payloads, filters outputs based on global `policies/scoping/` criteria, and logs the continuous audit trail straight to a single `evaluator_ledger.json` file.
