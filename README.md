# Jula Compliance-as-Code Workspace Spec

This repository houses the configuration components, data adapters, and executable rule criteria for the Jula Continuous Assurance Platform. It isolates high-level compliance checklists from raw execution code, delivering an automated, auditable security posture.

---

## 🛠️ Repository Architecture Blueprint

```text
jula-compliance-as-code/
├── workspace.yaml           # Core cloud providers only (no active_extensions)
├── catalog.csv              # Raw multi-framework corporate controls list
├── requirements.csv         # Intermediate engineering threshold triage sheet
│
├── engine/                  # Core Plumbing (Static & Hands-Off)
│   ├── integrations/        # Data collectors
│   │   ├── core/            # aws.yaml, azure.yaml, gcp.yaml, etc.
│   │   └── extensions/      # (Keep Empty Directory Placeholder)
│   ├── normalizers/         # Payload flattening Rego adapters
│   │   ├── core/            # aws/, azure/, gcp/, etc.
│   │   └── extensions/      # (Keep Empty Directory Placeholder)
│   ├── schemas/
│   │   └── extensions/      # (Keep Empty Directory Placeholder)
│   └── prompts/             # Centralized AI Prompt Contexts (MD templates)
│       ├── extract_requirements.md
│       ├── generate_policy.md
│       └── heal_normalizers.md
│
└── policies/                # Executable Policy Code Tier
    ├── scoping/             # Environment filters and global waivers
    └── rules/               # Flat, compiled core Rego policies (core_* only)
```

### 1. `workspace.yaml` (Root Directory)
The master orchestration configuration file acting as the platform's system boundary toggle switch. It explicitly declares which out-of-the-box core cloud providers (AWS, Azure, GCP) are active within this workspace. 

### 2. `catalog.csv` (Root Directory)
The active business compliance checklist framework provided by the risk team. It is a strictly pruned, 3-column spreadsheet (`Control_ID`, `Control_Statement`, `Control_Description`) exported from corporate GRC utilities. It is overwritten directly whenever master compliance frameworks are updated.

### 3. `requirements.csv` (Root Directory)
The intermediate engineering triage workspace generated by the AI. It structures unstructured prose from the catalog into clear technical parameters (such as expected values and operators) with a `PENDING` status column, allowing human operators to explicitly review, approve, or skip targets before they are compiled into code.

### 4. `engine/` (Central Platform Directory)
Houses the foundational, hands-off engineering properties defining how Jula interfaces with infrastructure systems.
- `engine/integrations/`: Dictates the connection parameters and credential scopes specifying exactly where and how collectors harvest infrastructure logs. Focuses purely on `core/` built-in clouds, with `extensions/` acting as an empty placeholder for future modular scaling.
- `engine/normalizers/`: Houses the OPA Rego scripts responsible for flattening complex native cloud provider payloads into uniform, predictable key-value fields. 
- `engine/schemas/`: A directory housing any structural layouts; `extensions/` is preserved as an empty scaffold.
- `engine/prompts/`: A centralized vault for text-based system prompts utilized by AI agents. Houses strictly templated constraints mapping the translation flow from business prose through policy compilation and autonomous self-healing of normalizer drift.

### 5. `policies/` (Executable Evaluation Directory)
The active, machine-readable gating tier evaluated by the Jula runtime engine.
- `policies/scoping/`: Global interceptor logic managing environmental exclusions, asset tagging context, and active corporate waivers.
- `policies/rules/`: The output landing zone for automated policy generation. It avoids complex folder hierarchies. All active evaluation rules live flat inside this folder (prefixed strictly as `core_*`) alongside a single `manifest.json` file tracking rule updates. Historical points-in-time are audited directly via Git version control tracking.

## 🔄 The 7-Step Operational Lifecycle

[1. Integrations] ──► [2. Normalizers] ──► [3. Import Catalog] ──► [4. Extract Requirements]
│
[7. Run Evaluation] ◄── [6. Generate Policies] ◄── [5. Review Requirements] ◄───┘

1. **Integrations:** Collectors utilize the credential parameters and endpoint mappings configured inside `engine/integrations/core/` to pull raw infrastructure metadata payloads based on the active core cloud platforms turned on in `workspace.yaml`.
2. **Normalizers:** Automated Rego data adapters process raw JSON responses from the clouds, flattening complex structures into predictable key-value properties.
3. **Import Catalog:** The risk team seeds the compliance workspace by dropping their master, multi-framework corporate control checklist directly into `catalog.csv`.
4. **Extract Requirements:** Leveraging centralized prompt contexts (`engine/prompts/extract_requirements.md`), Jula's AI reads the unstructured prose controls and extracts explicit, measurable technical constraints into `requirements.csv`.
5. **Review Requirements:** An intermediate spreadsheet workspace (`requirements.csv`) displays the AI's extracted parameters, allowing human operators to confirm, adjust, or skip constraints via the status column.
6. **Generate Policies:** Leveraging centralized prompt contexts (`engine/prompts/generate_policy.md`), an automated generation script reads approved rows from the spreadsheet and writes immutable, standalone `.rego` rule blocks directly into the flat `policies/rules/` directory.
7. **Run Evaluation:** The single centralized Jula evaluator engine ingests the rules directory, executes the core policies against live infrastructure payloads, filters outputs based on global `policies/scoping/` criteria, and logs the continuous audit trail straight to a single `evaluator_ledger.json` file.
